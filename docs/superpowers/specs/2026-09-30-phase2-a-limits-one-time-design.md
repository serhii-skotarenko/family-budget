# Phase 2 · Підпроєкт A — ліміти, разові витрати, аномальні суми

- Дата: 2026-09-30
- Статус: дизайн погоджено в брейнштормі, чекає ревʼю спеку
- Джерела: `docs/phase2-limits-proposal.md` (епік A, пропозиції №1 і №5),
  `docs/phase2-tasks.md` (T1, T2, T5–T12)
- Скоуп: tg-bot. MCP-конектор у цьому підпроєкті **не змінюється**.

## Контекст і мета

За вересень план на основі фактичних витрат вийшов хибним з двох причин. Перша — разові події:
85% категорії «Діти» були одноразовими. Друга — ліміти й прогрес доводилось рахувати вручну в
Excel. Мета підпроєкту — щоб бот сам:

1. тримав ліміти на тиждень/місяць (загальні й по категоріях) і показував прогрес із прогнозом;
2. розрізняв разові й регулярні витрати, щоб разові не спотворювали прогрес лімітів;
3. одразу звертав увагу на незвично велику суму під час додавання.

попередження показуються у відповідь на дію користувача.

## Зафіксовані рішення

| Питання | Рішення |
|---|---|
| Ліміт спільний чи персональний | Спільний на сім'ю |
| Залишок наприкінці періоду | Згорає, на наступний період не переноситься |
| Ліміт на групу категорій | Не в v1 |
| Валюта | Лише UAH, цілі гривні |
| Разові витрати у `/report` | Входять у загальну суму й суми категорій; окремо рядок «з них разових: X» |
| Разові витрати в лімітах | **Не** враховуються в прогресі, прогнозі й попередженнях |
| Ліміт встановлено посеред періоду | Діє на **весь поточний період**; `effective_from` лише визначає актуальний рядок |
| Видалення ліміту | Кнопка в `/limits`; у БД — рядок з `amount = NULL` (історія зберігається) |
| Прогноз на початку періоду | Показується завжди, з першого дня |
| Позначка «разова» в `/add` | Перемикач на екрані підтвердження; окремого кроку немає |
| Аномальна сума | Попередження на екрані підтвердження разом із підказкою позначити як разову; збереження не блокується |
| Ліміти в `/report` | Лише у звітах за тиждень і місяць, і лише ліміти того самого періоду; у річному звіті лімітів немає |
| Поріг попереджень після `/add` | ≥80% — попередження, ≥100% — перевищення; показуються щоразу, коли поріг перевищено, а не лише при першому перетині |

## Модель даних

Одна міграція Alembic `0002_limits_and_one_time`.

### Нова таблиця `limits`

| Поле | Тип | Примітка |
|---|---|---|
| `id` | int PK | |
| `household_id` | FK → households, `ondelete=CASCADE` | |
| `category_id` | FK → categories, nullable | `NULL` — загальний ліміт |
| `period_type` | `String(10)` | `"week"` \| `"month"` — значення наявного `periods.Period` (`WEEK`/`MONTH`) |
| `amount` | int, nullable | `NULL` — ліміт знято |
| `effective_from` | DateTime (UTC-naive) | момент встановлення |
| `created_by_id` | FK → members | |
| `created_at` | DateTime (UTC-naive) | |

Індекс: `(household_id, period_type, category_id, effective_from)`.

Рядки лише додаються, ніколи не оновлюються й не видаляються. **Активний ліміт** для пари
`(period_type, category_id)` — рядок з найбільшим `effective_from ≤ now` (при рівності — з
найбільшим `id`), якщо його `amount` не `NULL`.

### Зміна `expenses`

`is_one_time: bool`, `server_default false()`, not null. Наявні записи отримують `false`.
Downgrade видаляє колонку й таблицю.

## Бізнес-логіка

### `services/limits.py` (новий)

- `set_limit(session, household_id, member_id, period_type, category_id, amount) -> Limit`
  додає новий рядок з `effective_from = utcnow()`.
- `remove_limit(session, household_id, member_id, period_type, category_id)` додає рядок з
  `amount = NULL`. Якщо активного ліміту немає — нічого не робить.
- `active_limits(session, household_id, now) -> list[Limit]`.
- `limit_progress(session, household_id, period_type, now) -> list[LimitProgress]` рахує
  прогрес активних лімітів цього типу за поточний період (`periods.period_range`).
- `progress_for_expense(session, expense, now) -> list[LimitProgress]` повертає прогрес лише для
  лімітів, яких стосується витрата: ліміти її категорії та загальні, тижневі й місячні.

`LimitProgress` (frozen dataclass): `limit_id`, `period_type`, `category_id`,
`category_name | None`, `amount`, `spent`, `percent` (int, округлення вниз), `remaining` (може
бути від'ємним), `forecast`, `period_label`, `day_index`, `days_in_period`.

`spent` — сума **регулярних** (`is_one_time = false`) витрат у `[period.start, period.end)`, для
категорійного ліміту — лише в цій категорії.

### Прогноз (чиста функція)

`forecast(spent, days_elapsed, days_in_period) = round(spent / days_elapsed * days_in_period)`,
де `days_elapsed` — кількість днів від початку періоду до сьогодні **включно** (за Europe/Kyiv),
тобто завжди ≥ 1. Для тижня `days_in_period = 7`, для місяця — фактична кількість днів.

### Рівні статусу

- `ok`: `percent < 80` і `forecast ≤ amount`;
- `warn` (⚠️): `80 ≤ percent < 100` **або** `forecast > amount`;
- `over` (🔴): `percent ≥ 100`.

У `/limits` показуються всі три рівні. Після `/add` показуються лише ліміти з `percent ≥ 80`: сам
прогноз, без перевищення відсотка, попередження після додавання не викликає.

### Аномальна сума (`services/expenses.py`)

- `typical_amount(session, household_id, category_id) -> int | None` — медіана `amount` останніх
  20 **регулярних** витрат категорії (за `created_at desc`). Якщо таких записів менше 5 —
  `None`.
- Сума аномальна, якщо `typical is not None and amount > 3 * typical`. Константи
  (`ANOMALY_SAMPLE = 20`, `ANOMALY_MIN_SAMPLE = 5`, `ANOMALY_FACTOR = 3`) — на рівні модуля.

### Звіти (`services/reports.py`)

- `CategoryTotal` отримує поле `one_time: int`, `Report` — поле `one_time_total: int`. Загальні
  суми й частки не змінюються: разові в них входять.
- Анотацію лімітами робить обробник `/report`: для `Period.WEEK` / `Period.MONTH` він викликає
  `limit_progress` з відповідним `period_type` і передає результат у `format_report`. Для
  `TODAY` / `YEAR` ліміти не показуються.

### Експенси

- `create_expense(..., is_one_time: bool = False)`.
- `set_one_time(session, expense, member_id, value)` змінює позначку й записує
  `updated_by_id` / `updated_at`, як звичайне редагування.

## Інтерфейс бота

### `/setlimit` (новий роутер `limits.py`, FSM `SetLimit`)

1. Період: `[Тиждень] [Місяць]`.
2. Категорія: `[🌐 Загальний]` першою, далі категорії сім'ї.
3. Сума: «Введіть суму ліміту в гривнях» + «(зараз: X ₴)», якщо активний ліміт є. Перевірка —
   `parse_amount`.
4. Підсумок: «✅ Ліміт на місяць · Їжа: 12 000 ₴ (було 10 000 ₴)» або без «було», якщо ліміту не
   було.

`/cancel` перериває діалог на будь-якому кроці.

### `/limits`

```
📊 Ліміти

Місяць (жовтень, день 15 з 31):
• Загальний: 38 000 / 50 000 ₴ — 76%, лишилось 12 000 ₴
  прогноз: 78 533 ₴ ⚠️
• Їжа: 9 800 / 12 000 ₴ — 82% ⚠️, лишилось 2 200 ₴
  прогноз: 20 253 ₴

Тиждень (13.10–19.10):
• Кафе/кава: 1 300 / 1 000 ₴ — 130% 🔴 перевищено на 300 ₴
```

- Спершу місячні, потім тижневі; усередині — загальний першим, далі категорії за назвою.
- Inline-клавіатура: для кожного ліміту рядок `[✏️ <назва> · міс|тиж] [🗑]`, унизу
  `[➕ Додати ліміт]`.
  - ✏️ запускає `SetLimit` одразу на кроці суми з уже вибраними періодом і категорією.
  - 🗑 показує підтвердження «Зняти ліміт …?» `[Так] [Ні]`; «Так» викликає `remove_limit` і
    перемальовує `/limits`.
  - ➕ запускає `/setlimit` з першого кроку.
- Лімітів немає: «Лімітів ще немає. Додати — /setlimit» (плюс кнопка ➕).

### `/add`

- Екран підтвердження: у клавіатурі кнопка-перемикач `[☐ Разова]` / `[☑ Разова]` над
  `[✅ Зберегти] [❌ Скасувати]`. Натискання змінює `is_one_time` у FSM-даних і перемальовує той
  самий екран.
- Якщо сума аномальна, над «Перевірте запис:» стоїть:
  `⚠️ Сума значно більша за типову для «<категорія>» (звичайно ~<медіана> ₴). Все вірно? Якщо це
  одноразова подія — позначте її.` Медіана рахується один раз — на кроці вибору категорії (сума
  вже відома) — і зберігається у FSM-даних.
- Після збереження, якщо витрата регулярна, до підсумку додаються рядки з
  `progress_for_expense`, у яких `percent ≥ 80`:
  ```
  ⚠️ Їжа (місяць): 9 800 / 12 000 ₴ — 82%
  🔴 Загальний (тиждень): 10 400 / 10 000 ₴ — перевищено на 400 ₴
  ```
  Для разової витрати рядків немає.
- Підсумок збереженого запису показує «· разова», якщо позначку встановлено.

### `/list` і картка витрати

- Рядок списку й картка показують «· разова» для разових витрат.
- На картці є кнопка `[🔁 Позначити як разову]` / `[↩️ Зняти позначку разової]` → `set_one_time`
  → картка перемальовується.
- Редагування (`expense_edit`) поле `is_one_time` не змінює й попереджень про ліміти не показує.

### `/report`

```
Звіт: поточний місяць (вересень 2026)
Всього: 58 400 ₴ (з них разових 16 962 ₴)
  ліміт 50 000 ₴ — використано 83%

Діти: 19 921 ₴ (34.1%)
  з них разових: 16 962 ₴
  ліміт 4 000 ₴ — використано 74%
```

- «з них разових» з'являється лише коли сума разових > 0.
- Рядок ліміту використовує той самий `percent` (без разових), що й `/limits`.

### Інше

- `/setlimit` і `/limits` додаються в довідку `/start` і в меню команд бота. Кнопок у головній
  reply-клавіатурі не додаємо.
- Колбеки: новий `LimitCb(action: "period" | "category" | "edit" | "delete" | "delete_yes" | "add",
  period_type: str, category_id: int)` (`0` означає загальний) — і для діалогу `/setlimit`, і для
  кнопок `/limits`;
  `ExpenseCb` отримує дію `"toggle_one_time"`; `FlowCb` — `"toggle_one_time"` для екрана
  підтвердження `/add`.
- Новий роутер підключається в `build_router` до `fallback`.

## Обробка помилок і крайові випадки

- Невалідна сума в `/setlimit` — повідомлення від `parse_amount`, крок повторюється.
- Застаріла кнопка ✏️ або 🗑 для вже знятого ліміту — `callback.answer("Ліміт уже знято.")`.
- Застаріла кнопка перемикача після збереження `/add` — обробник прив'язаний до стану
  `AddExpense.confirm`, тож її перехоплює наявний `fallback` («Ця кнопка застаріла»).
- Позначка «разова» для чужої або видаленої витрати — `MISSING_EXPENSE_TEXT`, як у наявних
  діях картки.
- Витрата в категорії, для якої є лише загальний ліміт, враховується лише в загальному.

## Тестування

pytest, у стилі наявних `tests/test_services_*` і `tests/test_handlers_*`.

- **Чисті функції:** прогноз (перший день, останній день, 28/30/31-денні місяці), рівні статусу,
  медіана й поріг аномалії (менше 5 записів → `None`; межа `== 3 × медіана` не аномальна).
- **`services/limits`:** вибір активного ліміту з історії (кілька рядків, видалення, повторне
  встановлення), ліміт посеред періоду рахує весь період, разові не входять у `spent`,
  `progress_for_expense` повертає лише релевантні ліміти.
- **`services/reports`:** `one_time` по категоріях і загальний.
- **Міграція:** `0002` upgrade/downgrade на БД з наявними витратами (`is_one_time = false`).
- **Обробники:** повний діалог `/setlimit`; ✏️ і 🗑 у `/limits`; порожній `/limits`; перемикач і
  попередження про аномалію в `/add`; рядки лімітів після збереження (і їх відсутність для
  разової); позначка з картки `/list`; рядки лімітів і разових у `/report` (тиждень, місяць, рік).

## Поза скоупом

- MCP-конектор: `is_one_time`, ліміти й прогрес — підпроєкт C. До того часу аналітика конектора
  рахує разові витрати як звичайні.
- Заплановані платежі й амортизація — не робимо (підпроєкт B скасовано; великі нерегулярні платежі позначаються як «разові»).
- Проактивні повідомлення — підпроєкт E.
- Персональні ліміти, групи категорій, перенесення залишку, ліміти за довільний період.
